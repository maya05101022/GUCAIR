# Deployment guide — Render + PostgreSQL

GUCAIR runs on Render's free web-service tier with Render's free PostgreSQL instance.
SQLite is used only for local development. Neon PostgreSQL is documented as an
interchangeable alternative because the application only depends on `DATABASE_URL`.

## 1. Prerequisites

- GitHub account with the GUCAIR repository pushed:
  <https://github.com/maya05101022/GUCAIR>
- Render account connected to GitHub.
- Permission to create a Render Blueprint (database + web service) in the workspace.

## 2. One-click Blueprint deployment

1. Open <https://render.com/deploy?repo=https://github.com/maya05101022/GUCAIR>.
2. Sign in to Render and choose the target workspace.
3. Review the Blueprint. It creates:
   - `gucair-db` — free Render PostgreSQL 17, database `gucair`, user `gucair`, region `oregon`.
   - `gucair` — free Python web service in `oregon`, built with `./build.sh` and started with
     Gunicorn.
4. Enter the three prompted secrets:
   - `ADMIN_USERNAME` — production administrator username.
   - `ADMIN_PASSWORD` — strong password (12+ characters, not a common password).
   - `ADMIN_EMAIL` — administrator email address.
5. Apply the Blueprint and wait for the first deploy (5–10 minutes on the free tier).
6. Copy the service URL shown in the Render dashboard, for example
   `https://gucair-xxxx.onrender.com`.

`DATABASE_URL` is wired automatically from the Blueprint's `fromDatabase` reference, and
`SECRET_KEY` is generated by Render. No connection string is ever committed.

## 3. Manual web service (alternative)

Create the PostgreSQL instance first, then a web service:

- Runtime: **Python**
- Build command: `./build.sh`
- Start command:
  `gunicorn config.wsgi:application --bind 0.0.0.0:$PORT --workers 3 --timeout 120`
- Health check path: `/health/`
- Environment variables:

| Key | Value |
| --- | --- |
| `PYTHON_VERSION` | `3.13.5` |
| `DEBUG` | `False` |
| `SECRET_KEY` | generated long random value |
| `DATABASE_URL` | Render **internal** PostgreSQL URL (or any PostgreSQL URL) |
| `ALLOWED_HOSTS` | `localhost,127.0.0.1,.onrender.com` |
| `CSRF_TRUSTED_ORIGINS` | `https://*.onrender.com` |
| `ADMIN_USERNAME` | production administrator username |
| `ADMIN_PASSWORD` | strong production password |
| `ADMIN_EMAIL` | administrator email |
| `SEED_DEMO` | `True` for labelled demonstration records, otherwise `False` |

`RENDER_EXTERNAL_HOSTNAME` is supplied by Render. `config/settings.py` automatically adds
it to `ALLOWED_HOSTS` and `CSRF_TRUSTED_ORIGINS`.

### Using Neon PostgreSQL instead

1. Create a Neon project and copy the **pooled** connection string, which resembles
   `postgresql://USER:PASSWORD@ep-xxxx-pooler.REGION.aws.neon.tech/neondb?sslmode=require`.
2. Set it as `DATABASE_URL` and remove the Blueprint's `fromDatabase` reference (or delete
   the `databases` block entirely).
3. Keep `sslmode=require`; `dj-database-url` passes it to psycopg.
4. Nothing else changes: `build.sh`, migrations, seeding and the health check are identical.

## 4. Build sequence

`build.sh` performs:

1. `pip install -r requirements.txt`
2. `python manage.py collectstatic --noinput`
3. `python manage.py wait_for_db` (retries while the database starts)
4. `python manage.py migrate --noinput`
5. `python manage.py seed_data` or `seed_data --demo`
6. `python manage.py create_admin` (skips if admin variables are unset)

The build is idempotent: seeding uses `update_or_create`, and the admin command safely
updates an existing account.

## 5. Post-deployment verification

Replace `<service>` with the actual Render hostname.

1. `https://<service>.onrender.com/health/` returns HTTP 200 with
   `{"status": "ok", "database": "connected", ...}`.
2. Landing page shows consortium statistics from the production database.
3. `https://<service>.onrender.com/analytics/api/summary/` returns JSON.
4. Sign in as the production administrator.
5. Register a test representative, approve the institution, submit an assessment, and
   confirm the result, history and analytics update.
6. Check `/django-admin/` loads and is password-protected.
7. Confirm `http://` redirects to `https://`.
8. Confirm the README live URL exactly matches the verified address.

## 6. Common issues

| Symptom | Check |
| --- | --- |
| DisallowedHost | `ALLOWED_HOSTS` includes `.onrender.com`; redeploy after changing |
| CSRF verification failed | `CSRF_TRUSTED_ORIGINS` includes `https://<service>.onrender.com` |
| 500 on first request | Build logs: migrations, missing env vars, database URL |
| Static files missing | Build ran `collectstatic`; WhiteNoise middleware enabled |
| Database connection error | Database active, internal URL used, correct plan |
| Admin login fails | `ADMIN_USERNAME`/`ADMIN_PASSWORD` set before build; check build log |
| Free instance slow | Render free services spin down after inactivity |

## 7. Free-tier notes

- Render free PostgreSQL instances are time-limited and expire; Render emails a reminder
  before deletion. Export data or upgrade before the expiry date.
- Free web services spin down after 15 minutes of inactivity and cold-start on the next
  request (usually under a minute).
- The Blueprint can be re-applied at any time; it converges the service and database to the
  configuration in `render.yaml`.

## 8. Security checklist

- [ ] `DEBUG=False`
- [ ] Unique production `SECRET_KEY`
- [ ] `DATABASE_URL` stored only in Render environment settings
- [ ] `ALLOWED_HOSTS` restricted to the deployed hostname
- [ ] `CSRF_TRUSTED_ORIGINS` uses HTTPS only
- [ ] Strong administrator password
- [ ] HTTPS redirect and secure cookies active
- [ ] Local `.env` and `db.sqlite3` not committed
- [ ] Demo institutions labelled if `SEED_DEMO=True`
